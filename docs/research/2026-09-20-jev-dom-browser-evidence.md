# Jev DOM/browser evidence for Axiom Revenue Engine

**Research date:** 2026-09-20 (Toronto)
**Scope:** primary TypeSafe material plus narrowly selected open-source browser harnesses. No API key, account, live inference, browser session, prospect, or external side effect was used. Community measurements below are reported as measurements of those repositories, not as TypeSafe guarantees.

## What Jev actually does

TypeSafe’s official model is a typed decision function: application state goes in and independently declared `Choice`, `Score`, and `Noul` questions return bounded values and probabilities. It does not return prose, click a DOM node, navigate, wait for a network response, or own a browser. The surrounding program must turn a DOM/accessibility snapshot into state, enumerate candidate actions, execute the selected action, detect stale state, and verify the goal. TypeSafe’s docs and launch post describe this as structured decisions for code, not autonomous browsing ([API](https://docs.typesafe.ai/api), [introduction](https://docs.typesafe.ai/introduction), [launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev)).

That distinction matters for Axiom. A safe browser adapter can ask Jev to choose one operation and one element from a closed, host-generated candidate list, or classify visible evidence (for example, whether a page exposes a phone number or service-area phrase). The adapter—not Jev—must enforce same-page/fresh-node checks, URL policy, budgets, no-submit rules, retries, and independent verification. A generated string helper may fill a search field, but it is a separate model and capability. Jev is therefore element selection/classification inside a controlled loop, not a general browser agent.

The clearest implementation evidence is the MIT community repository [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast). Its code reads common visible HTML/ARIA controls, indexes them, sends an operation-plus-target decision to Jev, and checks the selected node and page guards again before input ([browser.py](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/browser.py)). Its documented limits are common controls only: no full accessible-name algorithm, shadow roots or frames, canvas, uploads, new tabs, nested scrolling, or arbitrary keyboard widgets. `DONE` is never independent proof of success ([performance limits](https://github.com/browser-use/jev-ultrafast/blob/main/docs/performance.md#limits)). This is an adapter design, not evidence that the hosted model itself supports every browser surface.

The official vendor organization is [github.com/typesafe-ai](https://github.com/typesafe-ai); the similarly named [github.com/TypeSafeAI/typesafe-playground](https://github.com/TypeSafeAI/typesafe-playground) explicitly describes itself as an independent community playground, not an official production agent. The [BunsDev fork](https://github.com/BunsDev/typesafe-ai-playground) is also community work. Their browser-oriented examples use a closed indexed action set, freshness checks, bounded calls, and an independent verifier. TypeSafe’s actual official playground entry point is the authenticated [console.typesafe.ai](https://console.typesafe.ai/). Treat the GitHub projects as integration examples only; none proves Axiom-site coverage.

## Numerical performance evidence and what it means

The official [Jev launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev) publishes an end-to-end TypeSafe service claim of **70–500 ms** and input price of **$0.042 per million tokens**; it says output is “FREE (too cheap to meter).” The post also says its published evals generally run from West Coast laptops. This is a provider claim, not an Axiom-region p50/p95 or browser-task SLA. The post’s workflow comparison reports **193.6× faster / 444.6× cheaper** on the home page, with four workflows against the average of Astra and Fable reference probabilities, but explicitly warns that workflows were made by the model-capabilities team, reference models are biased toward OpenAI/Anthropic, and the LLMs use TypeSafe’s structured wrapper. It does not establish DOM accuracy or lead-qualification accuracy. Output being published as free does not establish account-plan or contractual billing treatment.

The strongest browser trace located is [jev-ultrafast performance.md](https://github.com/browser-use/jev-ultrafast/blob/main/docs/performance.md). It reports a Google Flights task using pinned `jev-1.13.0` plus Mercury 2.5 for text: three alternating pairs, median original 9.450 s versus optimized 7.092 s, 25.0% lower; Jev requests 22→17 and browser protocol calls 1,092→101. It reports median Jev latency **178 ms**, 90,558 input tokens and 6,325 output tokens for the run, with total browser cost excluded. The page is unusually candid: only three pairs, sign-test p=0.25; live Google/network/routing/cache effects remain; the result is “not a broad agent benchmark.” It also reports separate smoke checks of 2.798 s (Wikipedia) and 1.896 s (local hotel fixture), not matched comparisons. This demonstrates an adapter can produce a fast verified trace; it does not show Jev alone is faster than an LLM browser agent, nor that the same latency holds from Ontario/Cloudflare.

## Browser-specific failure modes

The harness and official [Jev 1.13 jaggedness notes](https://docs.typesafe.ai/model-jaggedness/jev-1.13) point to concrete limits: Choice cardinality tops out at 255 (the harness keeps up to 240 elements); dense pages can truncate the target; dynamic DOM mutation causes stale decisions; incomplete autocomplete state can yield a wrong choice; hidden/covered/disabled controls need deterministic guards; and shadow DOM, iframes, uploads, canvas, nested scroll, hover menus, and unusual keyboard flows need separate adapters. A valid operation can still select the wrong target.

Page content is adversarial input. TypeSafe’s notes say injected instructions or misleading framing in state can move a result; reduce irrelevant state, filter it as data, and test hostile edge cases. They also flag context rot from large irrelevant state, unreliable numeric/date comparison, and non-guaranteed identity between independently asked probabilities. For Axiom, never allow page text to redefine the qualification policy, consent gate, URL allowlist, or send action. Keep policy and arithmetic in code; pass only the extracted evidence needed for the specific question; require a deterministic verifier and manual review for any consequential classification.

One further independent measurement is [WallerChen/jev-measured](https://github.com/WallerChen/jev-measured), which says it is unaffiliated with TypeSafe. Across eight small non-browser fixtures it reports first-party medians of 458–563 ms from one machine, with a measured 198.8 ms TCP floor; its five-question server-time probe was 70–81 ms. A 27-ticket, three-pass accuracy set tied Jev with Mistral Small (27/27 each) and was explicitly too small to rank models. These figures are useful experimental design guidance, not evidence of browser or Axiom qualification performance.

## Axiom evaluation proposal (not run)

Build an offline fixture corpus of 20–30 synthetic or legally captured public pages representing KW roofing, HVAC, and landscaping sites: clear service pages, weak/modern sites, contact forms, directory-like pages, dense navigation, hostile text, stale/mutated DOM, iframes, shadow roots, and no-contact cases. No form submission, login, CAPTCHA interaction, or prospect outreach.

The adapter should (1) extract a bounded, indexed list of visible links/buttons/fields plus URL/title/selected text; (2) ask Jev only closed-set `Choice` questions such as `evidence_kind`, `target_element`, and `stop_or_continue`, with a `Noul` question for “is this evidence sufficient?”; (3) apply URL, freshness, visibility, and action-budget guards in code; (4) independently verify the extracted URL/text and retain source URL, capture time, method, confidence, and model/prompt version. “Service category” should be a bounded enum with `UNKNOWN`; a site and industry alone cannot evidence rebuild qualification. This is transport shape only, not Axiom’s qualification prompt.

Compare against deterministic rules and, only if separately approved and budgeted, one LLM baseline with the same state and verifier. Measure per-page evidence precision/recall, wrong-target rate, false sufficiency, stale-action rate, truncation rate, verifier agreement, manual overrides, p50/p95 model latency, host extraction latency, end-to-end latency, retries, requests, and input tokens/cost. Report fixtures and failures separately by page class. A reasonable first gate is zero side effects, zero cross-origin navigation, zero policy bypasses, and a manually reviewed sample before any mailbox integration. Do not infer production readiness from a browser demo.
